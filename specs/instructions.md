# Instructions: Terraform Plan-Level Test Automation

Instructions for an AI agent to assess any Terraform module and implement plan-level `terraform test` coverage, along with a supporting CI workflow.

---

## Scope

This iteration covers:

1. Foundational changes (version constraints, directory structure).
2. Plan-only `terraform test` unit tests (no AWS credentials required).
3. A GitHub Actions CI workflow to run the tests on PR and push to `main`.

Out of scope for now: integration tests (apply/destroy), Terratest, security policy tests.

---

## 1. Assessment

Before writing any tests, the agent must:

- Read the module's `main.tf`, `variables.tf`, `outputs.tf`, and any sub-modules or upstream module sources.
- Identify the key behaviours: resource creation logic, conditionals, `for_each`/`count` patterns, `try()` fallback chains, naming conventions, and variable precedence.
- Identify what is testable at plan level (naming, conditional resource creation, data source logic, output structure) vs what requires apply-level tests (actual resource attributes behind module boundaries).
- Review any existing `example/` directory or documentation for expected usage patterns.
- Note any upstream modules that encapsulate resources — their outputs define what can be asserted through the module boundary.

---

## 2. Foundation

### 2.1 Add or verify `versions.tf`

Ensure a `versions.tf` exists at the module root with:

- `required_version >= 1.6.0` (minimum for native `terraform test` support).
- `required_providers` block declaring all providers used by the module (source and version constraint compatible with any upstream modules).

If `versions.tf` already exists, verify the terraform version is `>= 1.6.0`. If not, update it.

### 2.2 Add `.gitignore`

Ensure `.terraform/`, `*.tfstate`, and `*.tfplan` are gitignored.

### 2.3 Directory Structure

```
tests/
  plan/
    *.tftest.hcl       # Plan-level test files
    fixtures/          # Supporting files (JSON policies, YAML configs, etc.)
```

- Test files live in `tests/plan/`.
- Supporting fixture files (e.g. JSON policies for fallback testing) go in `tests/plan/fixtures/`.
- Tests run against the root module directly using inline `variables {}` blocks (not separate fixture modules).

---

## 3. Test Design Principles

### What to test at plan level

- **Naming and output logic** — anything computed from inputs that surfaces in outputs
- **Conditional resource creation** — `count` or `for_each` based on input values (e.g. KMS data source only created when a key is provided)
- **Variable precedence / fallback chains** — `try()` patterns where per-resource overrides common_options overrides module defaults
- **Edge cases** — empty inputs, null values, trimming behaviour
- **File loading** — `file()` calls with fallback paths (verify plan succeeds with valid/invalid paths)

### What cannot be tested at plan level

- Internal resource attributes behind module boundaries (tags, encryption config, etc. if the upstream module doesn't expose them as outputs)
- Provider-generated computed values (ARNs, IDs)
- Actual policy document content when generated by `data.aws_iam_policy_document` (mocked)

### Assertions

- Assert against `output.*` values where possible (these cross module boundaries)
- Assert against `data.*` and root-level resource attributes when accessible
- Use plan success itself as a valid assertion for input combination correctness
- Use `length()` checks for conditional resource creation (e.g. `length(data.aws_kms_key.this) == 1`)

---

## 4. Test File Conventions

- Use descriptive `run` block names that clearly state what is being tested.
- Group related assertions into a single `run` block where practical.
- Use inline `variables {}` blocks for clarity — each run block should be self-contained.
- Use `mock_provider` with `mock_data` to provide valid defaults for computed data sources:

```hcl
mock_provider "aws" {
  mock_data "aws_iam_policy_document" {
    defaults = {
      json = "{\"Version\":\"2012-10-17\",\"Statement\":[]}"
    }
  }
}
```

- This is needed because mocked providers generate random strings for computed attributes, which fail JSON validation on policy resources.
- Add `mock_data` blocks for any data source that produces values consumed by validation logic in downstream resources.

## 5. CI Workflow

### 5.1 Create `.github/workflows/terraform-plan-tests.yaml`

```yaml
name: Terraform Plan Tests

on:
  pull_request:
    types: [opened, reopened, synchronize]
    branches: [main]
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pull-requests: write

jobs:
  terraform-plan-tests:
    name: Terraform Plan Tests
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd

      - name: Setup Terraform
        uses: hashicorp/setup-terraform@b9cd54a3c349d3f38e8881555d616ced269862dd

      - name: Terraform init
        run: terraform init -backend=false

      - name: Terraform validate
        run: terraform validate

      - name: Terraform test
        id: terraform-test
        uses: Home-Office-Digital/core-cloud-workflow-terraform-actions/actions/test@main
        with:
          working-directory: .
          test-directory: tests/plan
          sonar-host-url: ${{ secrets.SONAR_HOST_URL }}
          sonar-token: ${{ secrets.SONAR_TOKEN }}
```

Key points:
- Use pinned commit SHAs for actions (not version tags) for supply-chain security.
- The test action from `Home-Office-Digital/core-cloud-workflow-terraform-actions` handles running `terraform test` and reporting.
- `test-directory` points to `tests/plan`.
- `workflow_dispatch` enables manual triggering from the GitHub Actions UI.
- No AWS credentials needed — all tests are plan-only with mocked providers.

## 6. Execution Steps (Agent Checklist)

1. **Assess** — read the module, identify resources, logic patterns, and testable behaviours.
2. **Foundation** — ensure `versions.tf`, `.gitignore`, and `tests/plan/` directory exist.
3. **Write tests** — create `.tftest.hcl` files with inline variables, mocked providers, and assertions.
4. **Validate locally** — run `terraform init -backend=false` then `terraform test -test-directory=tests/plan`.
5. **Iterate** — fix any failures. Common issues:
   - Mock provider generating invalid JSON for policy documents → add `mock_data` with valid defaults.
   - Asserting internal resource attributes through module boundary → switch to output-based or plan-success assertions.
   - File path issues in `file()` calls → ensure paths are relative to the module root.
6. **Add CI workflow** — create `.github/workflows/terraform-plan-tests.yaml`.
7. **Branch and PR** — create a feature branch, commit all changes, push, and open a PR.
8. **Verify** — confirm CI checks pass on the PR.
9. **Notify** — inform the team the PR is ready for review.

---

## 7. Quality Criteria

- All tests pass locally with `terraform test`.
- No AWS credentials required to run the test suite.
- Test file names and run block names are self-documenting.
- CI workflow triggers correctly on PR, push to `main`, and manual dispatch.
- No changes to existing module logic — this is additive only.
- PR is clean and reviewable.

---

## 8. Known Patterns and Workarounds

| Issue | Workaround |
|-------|-----------|
| `aws_iam_policy_document` mock generates invalid JSON | Add `mock_data` with `json = "{\"Version\":\"2012-10-17\",\"Statement\":[]}"` |
| Upstream module only exposes limited outputs | Assert on outputs + verify plan success rather than internal resource attributes |
| `file()` paths in the module are relative to module root | Test fixture files must also be relative to module root (e.g. `./tests/plan/fixtures/...`) |
| `try()` chains with invalid file paths | The fallback works — plan succeeds using the next valid path in the chain |
